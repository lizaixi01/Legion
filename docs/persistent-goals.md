# 持续目标

## 使用

开发版输入框开启“持续目标”，选择项目并输入目标。Manager 自行选择每轮的任务数量、Codex / Command Code 后端和并发数，调度仍通过现有共享队列与 DAG 执行器。

普通对话与持续目标是两种用户意图；持久化与恢复不再作为输入框中的模式开关。持续目标自动保存进度，历史工程任务仍可按原批准计划暂停和恢复；持续目标由 Manager 根据证据提出下一轮工作。普通聊天保存消息上下文，但尚不具备持续目标相同的执行检查点恢复能力。

默认上限为 24 小时、8 轮、64 次模型调用、64 次检查。Manager、Worker、独立挑战者的调用共同计费计数；上限不是承诺能够达到的稳定并发。暂停等待本轮收尾，恢复保留原截止时间和累计成本。退出应用会尝试暂停；不会在应用关闭后继续常驻执行，也不会在重启后未经操作自动恢复。

## 可验证的文件处理场景

项目中放置联系人 JSON 数组，每项包含 `name` 和 `email`。输入 `清洗联系人 contacts.json`（文件名可替换为简单 JSON 文件名）。系统在开始前冻结输入，Host 验证器独立计算期望值：

- 去掉姓名和邮箱首尾空白，邮箱转小写。
- 过滤缺少字符串字段、空姓名、邮箱格式不符合声明规则的记录。
- 按规范化邮箱去重，保留首次出现的顺序。
- 输出 `cleaned-contacts.json`，只含姓名和邮箱。

Worker 获得冻结输入副本。模型不能修改规则或期望值；独立挑战和 Host 外部 Node 验证都执行。即使源联系人文件随后变化，本次任务仍按创建时的输入验收。原文件不会被此流程覆盖。

其他目标可以派发执行，但没有已安装的领域验证器就不能声明验收完成。联系人场景是受限的数据清洗验证器，不代表任意数据任务、电子设计或建模已经支持。

## 恢复与证据

`.goals/<id>/run.json` 是带校验和的恢复记录，保存不可变配置、原始需求、轮次决策、任务、失败证据、候选、累计调用、检查次数和占用记录。JSONL 仅作审计。服务复用工程任务的所有权锁和持久化存储。

- 恢复前重新执行 Host 检查，不把磁盘里的 PASS 直接当作当前进程的信任凭证。
- 候选、报告、清单发生变化则阻塞。
- 安全边界是完整一轮结束；中途崩溃或未结算调用保守阻塞，不自动重派。
- 可以选择新的任务 ID、更换后端和并发，旧失败保留。
- 完成必须选择已验证候选，精确覆盖原始输出，再通过集成验证。
- 已完成和已取消任务不重复派发。跨轮依赖只能引用已验收的产物。

## 验证

`tests/persistent-goal.test.ts` 覆盖路线失败后的后端切换、暂停恢复、重验、篡改、预算、取消、未知执行、并发上限和联系人数据冻结。模型调用使用离线夹具；验证器运行真实 Node 子进程。

跨进程演示命令（三个命令必须使用同一个新目录）：

```powershell
npx tsx src/persistent-goal-demo.ts .local/my-goal-demo 1
npx tsx src/persistent-goal-demo.ts .local/my-goal-demo 2
npx tsx src/persistent-goal-demo.ts .local/my-goal-demo 3
```

本轮演示记录 `.local/persistent-goal-process-demo`，三个独立进程在同一目标上运行，epoch 1/2 暂停、epoch 3 完成；调用累计 4/6/7，截止时间不变。它证明恢复与验证接线，不证明真实模型的决策质量、混合后端稳定性或多日可靠性。
