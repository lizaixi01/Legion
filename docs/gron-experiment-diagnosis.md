# gron 对照实验诊断

日期：2026-09-28。只做事后分析，未修改候选源码、管理策略或重新运行模型，未重新进行完整官方评分。

## 1. 确认的评分环境缺陷

scripts/programbench/bridge.py 的 grade() 为解决测试依赖安装问题，将 HTTP_PROXY/HTTPS_PROXY 注入整个官方评分容器。被测程序也继承了这些变量。本地 127.0.0.1 HTTP 读取被转发到宿主代理，返回 502。

将 A/B 已冻结的源码分别在新的容器里原样重建，使用同一个本地 HTTP 服务返回 {"hello":1}：两份程序无代理时均 exit=0、输出正确；带评分器代理时均 exit=4、HTTP 502。诊断代码和原始结果位于 .local/diagnose-proxy.py、.local/gron-proxy-diagnostic.json。诊断容器已删除。

原官方过滤记录共 224 项：共同通过 155，只有 A 通过 11，只有 B 通过 4，共同失败 54。其中共同失败 26 项位于 URL 模块。不能由一个复现推断这 26 项全由代理造成，不能直接扣除它们重算分数。74.11%/70.98% 只保留为受污染环境下的历史观察，此处为修正前记录；修正后结果见文末。评分器 errorCode=null 并不能排除环境导致的语义错误。

## 2. 管理策略实际没有质量排序能力

src/team.ts 的 compete() 将同一任务复制给两个候选，区别只有路线提示；两者各自实现完整 CLI，没有模块分工、交叉验证或共享反例。本次两者各一次调用、决策均为 accept，没有触发修复。

候选结束后按声明顺序检查，首个通过复查即返回。本次 candidate-1 通过四个简单公开案例，因此 candidate-2 无法改变选择结果。它只有在 candidate-1 未通过时才提供后备价值。candidate-2 没有官方评分，不能断言它更好或更差。这不是 best-of-2，也未验证模型 Manager 的价值。

## 3. 检查提供的区分能力不足

公开案例只覆盖简单对象、数组、嵌套结构及一次反向转换。重复重建这些案例可证明可复现，不能增加功能覆盖。两者都通过后，管理器没有区分实现质量的证据。投入第二份完整实现，未伴随更有区分能力的验证机制。

## 4. 当前实验不能推出 Coding 不适合 Multi-Agent

当前任务是一个完整 CLI 的行为复现，实验方式是重复实现后择一，不是并行处理多个独立交付物，也没有验证带互补分工的工程流程。因此只能诊断当前任务/调度/检查组合，不能外推所有 coding 场景。

此外只有单题各一次可评分运行；A 的首次超时因执行器缺陷丢失提交和完整用量，修复后才重跑；A/B 的适配器版本有基础设施差异。token 的 1.74 倍是所列有效运行的观察值，不是完整实验成本比，也不是稳定效果估计。

## 下一步顺序

1. 将依赖下载所需网络配置与被测程序的运行环境分离，加入本地 HTTP 的环境回归检查。不能仅给所有测试加 NO_PROXY=*，那可能改变原本在测试的显式代理行为。
2. 保持两份 submission.tar.gz 和哈希不变，只重新评分，不再调用 Worker。保留历史分数并新增纠正记录。
3. 再判断实现能力差异；后续策略验证使用未调优任务。当前 gron 已做隐藏测试事后诊断，只能作为开发/诊断题。

暂不扩大 Agent 数量，也不依据当前受污染的分数转向另一个行业场景。
