# Benchmark 驱动的可用版迭代

2026-10-04 当前优先级：完成产品边界清理、离线验收和工作分支提交推送。历史基准协议与结果独立保全，本轮不运行真实模型或 benchmark。后续平台扩展、性能评测和安装更新需要新的任务范围。

## 当前执行顺序

1. 根据原始失败记录修复执行/验收/计量缺陷，每项先做离线故障回归，再进入新的冻结批次。明确区分模型解题不足、管理决策问题、检查覆盖不足和执行器故障。
2. 接通代码工程小批三臂，检验预算、指标和终局评测器；试跑稳定后，用新的 20–30 题冻结正式集。优化用开发集，主要效果看未调优集；失败或负结果也保存并公开。
3. 在用户工作流中验证可用版门槛，再安排平台分发。benchmark 成绩与产品稳定性分别报告。

每轮记录实现提交、协议/输入/工具链身份、改变的因素、质量、成本、墙钟和人工维护。候选更多、token 更多或一次得分更高本身不构成版本改进。策略自己的预算不足与基础设施中断保持不同归因，不允许择优替换 primary run。

## 通用决策与恢复约束

决策必须有成功终态及完整可解析结果后才能派工；截断和提供商失败保留可观测用量，缺失用量保持未知，不重复计算快照与终态用量。显式超时和有效配置绑定运行身份，恢复不能静默改变条件、清零原预算或重放不确定调用。

独立尝试目录、进度事件及故障收尾保留；目录数不等于已确认提供商调用次数。当前离线验证与审计见[产品清单](product-boundary-audit.md)，历史修复与实验记录在独立归档保全。

## 第一版可用性的建议门槛

先围绕本地代码工程的完整交付收敛：输入需求、执行、集成、验收、暂停/恢复、交付。以下门槛需要实际验证，尚不是已经达到的承诺：

- 多模块真实任务能形成可获取、可复验的确定候选；整合结果重新检查，未覆盖要求清楚保留 unverified。
- 模型/网络/额度/验证器故障有可读原因和原始证据；停止、取消和恢复不会重复启动未知调用、补充配额或将旧 PASS 当新认证。
- 需求、输入、测试、运行环境与候选版本绑定；修改或缺失会使旧证据失效。
- Manager、Worker、Challenger、验证及重试均有可对账成本和阶段进度，能够说明交付提升及其代价。
- 用目标用户的真实工作流做端到端试用，记录监督、维护、验收和返工时间；经过用户验收的可用性不能由 benchmark 分数替代。

三臂指标定义与准备状态见[实验协议](three-arm-engineering-protocol.md)，已有结果与证据覆盖见[架构说明](architecture-boundaries.md)，共享环境保护见[并行开发说明](benchmark-safe-development.md)。平台发放前再检查安装、更新、权限、依赖授权、升级/回滚和支持范围，当前不扩展这些发布工作。
