# Benchmark 驱动的可用版迭代

2026-10-02 用户确定当前优先级：跑 benchmark、依据结果优化，形成正式可用版本，再安排各平台发放。代码和实验资料继续按既有 Git 工作流保存；平台扩展、发布渠道和安装包推广放在可用版之后。

## 当前执行顺序

1. 完成正在运行的冻结 HWE 深度比较，保留全部尝试、修复、资源与候选。当前批次不注入开发代码；S/D 结果齐全、候选独立复验后再判断增加搜索深度是否值得。
2. 根据原始失败记录修复执行/验收/计量缺陷，每项先做离线故障回归，再进入新的冻结批次。明确区分模型解题不足、管理决策问题、检查覆盖不足和执行器故障。
3. 接通代码工程小批三臂，检验预算、指标和终局评测器；试跑稳定后，用新的 20–30 题冻结正式集。优化用开发集，主要效果看未调优集；失败或负结果也保存并公开。
4. 在用户工作流中验证可用版门槛，再安排平台分发。benchmark 成绩与产品稳定性分别报告。

每轮记录实现提交、协议/输入/工具链身份、改变的因素、质量、成本、墙钟和人工维护。候选更多、token 更多或一次得分更高本身不构成版本改进。策略自己的预算不足与基础设施中断保持不同归因，不允许择优替换 primary run。

## 首项有证据的修复：Manager 决策窗口

深度批次首次 S 尝试在派发 Worker 前被固定 300 秒窗口截断，模型虽输出完整形状的决策，却没有成功终态与 response.json；运行方对称扩大 S/D 冻结副本窗口并重新封存哈希，第二次 S 才继续到后续轮次。这是基础设施诊断，不是管理策略收益证据。

开发版本将 HWE Manager 默认决策窗口设为 900 秒；`manager.timeoutSeconds` 可显式指定 30–1800 的整数。每次决策扣除上下文准备耗时，并将宿主调用超时限制在该轮剩余总预算以内。全局取消/期限仍由原运行信号控制；较长局部窗口不增加总期限、Worker 配额或允许检查失败。

实际限制写入 `decision-invocation.json`。模型日志必须有成功终态且桥接层未超时；完整形状的 JSON 不足以继续派工。日志可解析时，对截断/提供商失败保留桥接层末次 usage 供成本核对；不能将缺少完整 turn 用量记成零，也不能把 snapshot usage 与已记录的终态 usage 重复相加。

显式 timeoutSeconds 是冻结配置的一部分，恢复时不能静默改变。未填写该字段的历史配置仍可解析，不自动补字段或改写旧 state；复现旧 300 秒行为应使用旧冻结实现，或在新实验明确写 300。每个新批次仍须绑定实际实现，不能只凭“同一 config”认定条件相同。本修复不迁移正在运行的批次，也不重写首次失败记录。

补测发现决策失败后恢复会重复使用同一 `round-轮数-历史长度` 目录并因 EEXIST 再次失败。开发版本保留原目录，用独立 retry 目录记录后续尝试，派发决策前追加 `decision_started` 进度事件。恢复仍先停止原 owner，沿用冻结配置、累计耗时与 Worker 预约；没有自动恢复或重置预算。汇总包含原失败与重试的有效 usage，并单列尝试目录数及有/无有效用量的数量；目录还包括准备阶段，不能冒充实际提供商调用次数。未知用量保持未知成本。

## 第一版可用性的建议门槛

先围绕本地代码工程的完整交付收敛：输入需求、执行、集成、验收、暂停/恢复、交付。以下门槛需要实际验证，尚不是已经达到的承诺：

- 多模块真实任务能形成可获取、可复验的确定候选；整合结果重新检查，未覆盖要求清楚保留 unverified。
- 模型/网络/额度/验证器故障有可读原因和原始证据；停止、取消和恢复不会重复启动未知调用、补充配额或将旧 PASS 当新认证。
- 需求、输入、测试、运行环境与候选版本绑定；修改或缺失会使旧证据失效。
- Manager、Worker、Challenger、验证及重试均有可对账成本和阶段进度，能够说明交付提升及其代价。
- 用目标用户的真实工作流做端到端试用，记录监督、维护、验收和返工时间；经过用户验收的可用性不能由 benchmark 分数替代。

三臂指标定义与准备状态见[实验协议](three-arm-engineering-protocol.md)，已有结果与证据覆盖见[实验摘要](experiment-summary.md)，共享环境保护见[并行开发说明](benchmark-safe-development.md)。平台发放前再检查安装、更新、权限、依赖授权、升级/回滚和支持范围，当前不扩展这些发布工作。
