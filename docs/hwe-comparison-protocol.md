## 问题

在同一 RV32IM baseline、公开检查和本机环境下，多轮管理是否比普通 Codex 的一次完整执行获得更好的有效 CoreMark 性能？同时记录代价和人工介入。开发试跑不计入这次对照。

## 主对照

| 项目 | 普通 Codex | Management＋Subagent |
|---|---|---|
| 起点 | 同一个冻结 baseline | 同一个冻结 baseline |
| 实现模型 | GPT-6 Sol / medium | GPT-6 Sol / medium |
| 管理模型 | 无 | GPT-6 Sol / high |
| 会话 | 一个完整会话，自行选择方法 | 至多 2 轮，每轮至多 2 个隔离 Worker |

这里允许管理组花更多总计算量，且管理推理强度单独列出；不把结果解释为纯粹的“架构因果效应”。若后续需要区分管理策略与计算量贡献，另做等总预算或等调用次数消融。

## 测量和停止

- 正确性门槛：lint、构建、公开 ISS/CRC cosim、bounded ALTOPS formal、综合及有效三种 seed FPGA 测量。至少两个 seed 成功的规则沿用上游。
- 质量：最终可交付设计的 CoreMark iter/s；同时列 Fmax、LUT4、周期数和各 seed。未通过门槛的产物不记作有效性能。
- 普通组提交其最终源码；管理组提交程序根据外部证据选择的最佳源码，必要时保留已验证 baseline。分别列出是否改善 baseline。
- Token：Manager 与所有 Worker 的输入、缓存输入、输出。缓存输入已经包含在输入中，不重复相加。缺失用量明确标出。
- 耗时：从启动到最终外部验证完成，包括模型、调度及检查；基线环境准备时间单独报告。
- 人工介入：区分修改假设/源码与恢复基础设施。正式运行中不向模型补充人工解题提示；故障不得悄悄重跑后择优。
- 隐藏测试、官方最终评分反馈不进入模型上下文。本轮结论限于这些公开检查与本机工具链。
- 每组先完成一次；不由单个任务估计通用成功率，也不把增加 token 本身作为收益。
